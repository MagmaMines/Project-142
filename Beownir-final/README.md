# Beownir

A single-file browser IDE: editor, terminal, virtual filesystem, a Node-compatible
worker runtime, streamed npm-compatible package installer, and virtual-HTTP live
preview. The static-host mode follows the same broad browser-first pattern as
NodePod: JavaScript executes in browser workers against a virtual filesystem and
network adapters, not as an OS Node process. `beownir-standalone.html` opens a
working, explicitly limited development environment without a project server;
the separate WASIX profile is optional and has additional runtime-package and
host requirements.

**First run** shows a "what works in this browser" card whose every line is
probed live (cross-origin isolation, SharedArrayBuffer, JSPI, OPFS, service
worker, host bridge) — the same list backs the "This device" tab in Help, so a
visitor never has to guess why a capability is missing.

file and a candidate-status notice. It intentionally does not publish anything:
package metadata is still private/UNLICENSED, and commercialization requires the

the remaining native Node/WASIX acceptance gates. See
[WASIX_PRODUCT_ROADMAP.md](WASIX_PRODUCT_ROADMAP.md).

## Quick start

```bash
npm test          # 327 tests: installer, host, runtime, shell, CLI, crypto, DNS, polyfills, storage, deployment, standalone build and tooling
npm run compat    # measured Node API coverage + the first missing exports per module
npm run check     # static checks on the single file (scripts, ids, assets)
npm run sync      # re-inline runtime sources + the host into o/site/index.html
node tools/native-assets.mjs --extract   # refresh o/native/ from the HTML pack
node tools/native-assets.mjs --embed     # write o/native/ back into the HTML pack
npm run verify    # sync --check, static checks, artifact --check, compat floor and the whole test suite
npm run differential # 111 behaviours compared snippet-by-snippet with the running Node
npm run build:standalone # build beownir-standalone.html
npm run standalone:check # fail when the committed artifact is stale or tampered
npm run standalone:smoke # boot the artifact on its own and run real commands
npm run reports   # regenerate the five reports from measurements
npm run release:candidate # build an integrity-checked internal bundle under dist/beownir-candidate
npm run deploy:headers # verify o/site/_headers matches netlify.toml (Cloudflare reads it)
npm run deploy:check -- --ide https://your-site.example/  # check a live deploy
npm run host      # serve the IDE on http://localhost:4173 (runtime 4174, preview 4175)
npm run serve:static # serve the deploy artifact with the Netlify headers on :8080
```

Requires Node 18.17+ for the test suite and the host.

## Browser support

| | Floor | Notes |
| --- | --- | --- |
| Chrome / Edge | 85 | Everything in this README works, including the service-worker preview and offline shell. |
| Firefox | 79 | Same, with one caveat: the service-worker preview path is Chromium-tested only (see below). |
| Safari | 14 | Same caveat; WebKit is untested (no runner in CI). |

The floor is enforced, not aspirational: `npm run check` fails the build if the
shipped bundle uses an unguarded language feature newer than the floor
(`Object.hasOwn`, `String.prototype.replaceAll`, `Array.prototype.at`,
`structuredClone`, `Promise.withResolvers`, `Array.fromAsync`,
`Array.prototype.findLast`, `AbortSignal.timeout`). Platform features are not in
that list because they are probed at boot and degrade with a visible reason
rather than crashing: service worker, SharedArrayBuffer/JSPI, OPFS,
CompressionStream, IndexedDB/localStorage, WebCrypto.

What is *not* a support question: the native browser-WASM profile needs
cross-origin isolation (SharedArrayBuffer + JSPI), which Safari only exposes
inside a dedicated worker (no JSPI on the main thread as of Safari 18), so that
profile is Chromium-only by design. And this release has been **verified in
Chromium only** — the degraded-engine tests simulate missing APIs in a VM, which
is not the same as running on Gecko. Treat Firefox/Safari as "should work from
the feature floor, unverified here" until someone runs the suite in those
engines.

## Embedding the runtime in your own web IDE

The IDE's runtime is also shipped as **one drop-in file**,
`o/embed/beownir-kernel.js` (5.6 MiB, generated from the application's own
sources so it cannot drift). If you build your own HTML/CSS IDE, add one
script tag and you get the virtual filesystem, `node`, `npm install` from the
real registry, and virtual dev servers on an in-page loopback — with named
errors (`EPERM`, `ENOSYS`, `EAGAIN`, `Unknown command: …`) for the things a
page cannot do:

```html
<script src="beownir-kernel.js"></script>
<script>
  const kernel = BeownirKernel.create();
  kernel.whenReady().then(async () => {
    await kernel.writeFile('app.js', "console.log('hi from your own IDE');\n");
    console.log(await kernel.run('node app.js'));
  });
</script>
```

The full API, the security model (sandboxed opaque-origin iframe, your page's
CSP never needs `unsafe-eval`), the measured 16/16 headless-Chromium test
suite and the honest list of limits are in **[EMBEDDING.md](EMBEDDING.md)**.
`npm run embed:e2e` re-runs the suite; `npm run check` fails a release if the
bundle is stale or breaks the browser floor.

## Two runtimes

| | Limited compatibility engine | Native browser-WASM profile |
|---|---|---|
| Where | worker inside the page | isolated origin (`PORT+1`) |
| Node API | curated shim (`fs`, `net` loopback, `http`, `crypto`, `zlib`, `child_process` over workers, …) | portable Node build in WASM |
| npm | streamed installer in the worker | real npm/pnpm inside the VM |
| Needs | nothing | COOP/COEP, SharedArrayBuffer, JSPI |

The limited engine is always available. The native profile activates when the
page is cross-origin isolated and the host serves the runtime origin.

## Installing big packages ("packets")

`registry size exceeded` came from buffering a whole tarball in one response.
The installer now never holds a complete tarball:

1. a single `Range: bytes=0-0` request per registry origin (cached for the
   session) proves that ranges are honoured;
2. the tarball is cut into 4 MiB byte ranges fetched by up to three parallel
   requests, each retried and resumed from the last received byte;
3. no total size is needed: the last packet arrives shorter than requested (or
   the next offset is rejected with 416) and ends the stream. Browsers only
   expose CORS-safelisted response headers, so `Content-Range` and
   `Content-Length` are never required;
4. packets are handed to gzip → tar → filesystem **strictly in order**, so peak
   memory stays near `concurrency × segmentBytes` (about 12 MiB) regardless of
   package size;
5. SHA-512 is computed while streaming and checked before the transaction
   commits; a mismatch rolls the whole install back;
6. registries that ignore ranges fall back to a single stream automatically.

Verified end-to-end against the live registry: `next@16.4.3` installs 10,152
files / 186 MiB in about 28 s inside the worker. `node_modules` never enters the
editor's source workspace; it is compressed into a dependency checkpoint and
restored after a reload.

## Preview: native modules where it is safe, a rewriting loader everywhere else

Two preview paths exist and the IDE chooses between them per page load.

**Same-origin service worker (default on loopback).** When the page is served
from `localhost` / `127.0.0.1` / `::1` *and* a service worker is controlling the
page, `o/site/coi-sw.js` turns the IDE origin into a proxy for the project's
virtual dev ports. The preview frame is loaded from
`/__beownir_preview__/<port>/<path>`; the worker forwards each request to the
open IDE tab, which answers it from the worker runtime's virtual loopback. Once
a preview document has claimed its client, that client's root-relative
subresources (`/src/main.js`, `/style.css`, `/logo.svg`) route to the same
virtual port, so the page runs as a normal origin: ES modules load natively, Vite
serves `/@vite/client`, assets stream as usual. For HTML documents the worker
injects a small WebSocket shim that bridges `ws://` to the IDE tab over a
`BroadcastChannel`; the tab feeds those frames into the same kernel upgrade path
the srcdoc preview uses. The result is framework HMR — a Vite update reaching a
real `import.meta.hot` handler and touching the DOM — without a reload or a
rewritten transport.

**Sandboxed `srcdoc` (deployed and non-loopback).** Everywhere else — every
hosted deployment of the IDE, and any browser where the worker is not
registered — the preview stays an opaque-origin `srcdoc` iframe and modules go
through the rewriting loader (`o/runtime/preview-bridge.js`), with the same
live-reload behaviour as before. The same worker is served from a static host,
so a deployment that loses `/coi-sw.js` degrades to this path rather than
failing.

Why the split is deliberate: the service-worker path gives the project's code
same-origin privileges on the IDE origin. That is fine for a developer running
their own project on their own machine, and it is exactly what Nodepod-style
previews do. It is not something to hand to a hosted multi-tenant IDE without a
separate origin, so the gate is loopback-only and the deployed path keeps the
sandboxed frame.

Under either path the IDE's own live reload still runs for projects without a
framework dev server:

- every save marks the file changed; live reload waits for the write to settle
  (500 ms web / 1500 ms native) and refreshes the preview;
- the preview bridge captures scroll position, typed form values and focus
  before the reload and restores them afterwards;
- `node_modules`, `.beownir`, build output and VCS directories are ignored so a
  dependency install does not trigger a refresh storm;
- the toggle in the preview header disables it, and the state chip shows
  `Live` / `Manual`.

Native browser-WASM dev servers keep their own framework HMR; the IDE does not
interfere with it.

## Storage, quotas and the "quota exceeded" error

Next.js builds write 100–400 MiB of `.next` output. When that output was packed
into the dependency checkpoint, the origin quota ran out and the runtime echoed
the browser's own `QuotaExceededError` text as "Storage capacity quota
exceeded". The fix is structural, not cosmetic:

- checkpoints never include `.next`, `.nuxt`, `.output`, `dist`, `.cache`,
  `.npm`, `.pnpm-store`, `coverage` or npm's staging directories — all of that
  is rebuildable;
- a storage governor (`o/native/storage-manager.mjs`) reads
  `navigator.storage.estimate()`, keeps 10% headroom, and preflights installs
  (512 MiB) and builds (384 MiB), refusing an impossible command up front with
  an actionable message instead of failing halfway through;
- a quota failure while committing a checkpoint triggers exactly one garbage
  collection of stale per-group OPFS mounts and rebuildable caches, then a
  single retry;
- startup asks for `navigator.storage.persist()` and sweeps execution mounts
  left behind by an earlier session (`workspace-0x8…`);
- quota errors are reported once, in plain language, with the next step.

The source workspace is no longer a fixed 64 MiB. It is half of whatever the
origin can actually store — floored at 64 MiB and capped at 20 GiB — with a
quarter of that per file and 20,000 entries. The number comes from
`navigator.storage.estimate()` at boot, is enforced by the editor, the importer,
the runtime filesystem, `statfs`/`df` and the browser kernel, and is printed by
`storage df` with the quota it came from. Autosave stores one IndexedDB record
per distinct file content (keyed by its SHA-256) plus a small manifest under
`current`/`previous`, so a multi-gigabyte workspace never has to fit in a single
value and a debounced save writes only the files that changed.

The terminal exposes the same controls: `storage df` (usage, quota, policy,
workspace size), `storage gc` (frees checkpoints, build output and stale
mounts), `storage persist` (asks the browser for persistent storage). The IDE
adds Help → Storage with the same numbers and buttons, and autosave or
checkpoint writes that hit the quota point at it instead of failing silently.

## Terminal

The terminal is a small POSIX-flavoured shell, not an operating-system shell:

- quoting (`'…'`, `"…"`, backslash), `$VAR` / `${VAR}` / `$?` expansion and
  `NAME=value command` prefixes;
- pipelines (`a | b`), redirection (`>`, `>>`, `<`, `2>`, `&>`), `&&` chains and
  globbing (quote a pattern to disable it);
- commands: `ls cat head tail wc grep sort uniq cut tr tee sed find stat du df
  storage tree touch mkdir rm cp mv ln chmod echo printf basename dirname
  realpath date sleep xargs env export unset source history time test [ true
  false which curl wget clear`, plus the runtime commands `node npm npx esbuild
  serve ps kill ports open close-port`;
- `npm run <script>` executes package scripts through the same shell;
- `command --help` prints one-line usage, and unsupported syntax (`;`,
  background jobs) fails loudly instead of being mis-parsed.

## How compatible is it, really?

Measured, not asserted — the repository does not ask you to take a number on faith.
`npm run compat` starts from **Node's own module list**, not from the modules the
runtime happens to expose, compares every export with the running Node and prints
a table:

```
module               cover   runtime/node   first gaps
crypto               100.0%      67 /67
module               100.0%      32 /30
...
overall 100.0% of 1336 Node exports across 55 modules (55 implemented) on Node 22.22.3
deprecated internals (_*): 0.0% of 53 exports across 11 modules, reported separately
```

Scoring from Node's list is the point: an earlier revision iterated
`Object.keys(CORE)`, so a builtin that was missing entirely — `console`, `dgram`,
`repl`, `sys`, `trace_events`, `wasi` were all absent — simply vanished from the
denominator instead of scoring zero. Those six are now implemented, `require()`
agrees with `module.builtinModules`, and a module that stops existing can only
make the number go *down*.

All `1336` public Node exports across all `55` modules now exist on the exported
surface (`100.0%`), including `crypto.X509Certificate` (PEM/DER certificate
parsing, `subject`/`issuer`/`subjectAltName`/`infoAccess`, host/email/IP/issuer/private-key/signature
checks, `toLegacyObject()`), `crypto.Certificate` (SPKAC `verifySpkac`,
`exportPublicKey`, `exportChallenge`), `crypto.createECDH` (P-256/P-384/P-521
with compressed/hybrid point codecs and `ECDH.convertKey`), and `crypto.scrypt`
— compared against OpenSSL in `test/crypto.test.mjs` and
`test/crypto-asymmetric.test.mjs`.

The deprecated `_`-prefixed internals (`_http_agent`, `_stream_readable`, …) are
Node's own implementation details, not API. The runtime does not ship them and
does not advertise them in `builtinModules` — advertising a module that cannot be
loaded is exactly the failure mode described above.

The baseline (`o/compat/node-compat.json`) is committed and `npm run verify` fails
if coverage drops, while `test/compat-report.test.mjs` fails if any single module
gets worse. That makes the number a regression test instead of a slogan.

Compatibility bugs fixed while closing the gap to 99.3%:

- **`util.getSystemErrorName(-2)` returned `'ERRNO_-2'`** and `getSystemErrorMessage`
  returned `'system error -2'`, so code that maps errno numbers to names (every
  loader that prints a friendly `ENOENT`) got nonsense. There is now one libuv
  errno table behind `util.getSystemErrorName`, `util.getSystemErrorMessage`,
  `util.getSystemErrorMap()`, `os.constants.errno` and `os.constants.priority`,
  so an errno can never disagree with itself, and `EWOULDBLOCK` still reports as
  `EAGAIN` the way libuv does.
- **`os.constants.errno` was an empty object** — `os.constants.errno.EACCES` was
  `undefined`. It now carries the full table (85 names).
- The deprecated-but-exported `util.is*` predicates (`isBuffer`, `isObject`,
  `isPrimitive`, …), `util.toUSVString`, `util._extend` and
  `process.loadEnvFile()` (dotenv parsing that never overwrites an existing
  variable, exactly like Node) were missing entirely.

The loader and the CLI surface had real defects too, each reproduced with a
package from the registry before it was fixed:

- **`readline` interfaces never emitted `'line'`.** `createInterface()` returned an
  EventEmitter with a `question()` method and nothing else, so a CLI reading stdin
  by line (`cat data | tool`, a REPL loop, `inquirer`) received nothing and hung.
  It is now a real interface: CRLF-aware line buffering, `'line'`/`'close'`/
  `'pause'`/`'resume'`, `question()`, async iteration, `setPrompt`/`prompt`, and
  `readline/promises` with a promise-returning `question()` and `Readline`.
- **`package.json` `"imports"` maps (`#internal` specifiers) did not resolve**, so
  chalk, ora and `@babel/core` died with `Cannot find module '#ansi-styles'`.
  `#name` specifiers now resolve through the nearest `package.json`, including
  `*` patterns, and fail with Node's `ERR_PACKAGE_IMPORT_NOT_DEFINED`.
- **Import attributes (`import data from './x.json' with { type: 'json' }`) were
  left in the rewritten output**, producing a `SyntaxError` (cli-spinners, ora).
- **Slash subpath builtins did not exist**: `require('path/win32')`,
  `path/posix`, `util/types`, `stream/consumers` and `inspector/promises` all threw
  `MODULE_NOT_FOUND` (execa imports `path/win32`). `path.win32` was also the posix
  object with a different `sep`, so `path.win32.join()` returned forward slashes.
- **`module._resolveFilename` was missing**, so `module-alias`-style patching threw.
  `Module` now carries `_resolveFilename`, `_nodeModulePaths`, `_findPath`,
  `_load`, `_extensions`, `_cache` (the real `require.cache`), `globalPaths`,
  `constants`, `findPackageJSON`, `runMain` and the compile-cache/source-map
  stubs, and `require()` resolves through `_resolveFilename` so a patch takes
  effect.
- **`process.env` did not coerce to strings.** `process.env.PORT = 3000` stayed a
  number and `= undefined` vanished, unlike Node (`'3000'`, `'undefined'`);
  `process.env = {...}` now replaces the object too.
- **`process.browser` was `true`.** TypeScript checks it to decide whether it may
  touch `fs`/`path`, so `require('typescript')` silently degraded to a version-only
  stub and `createProgram()` crashed. Node defines no `process.browser`; the
  runtime no longer does either, and typescript 5.9.3 compiles.
- **`fs.glob`/`globSync` were missing and `path.matchesGlob` mishandled `**`** —
  `src/**/*.js` did not match `src/a.js` (a globstar segment must match zero
  directories). `fs.glob`, `fs.globSync`, `fs.exists`, `fchmod`, `fchown`,
  `futimes`, `lutimes`, `chown`, `readv`/`writev`, `fsync`/`fdatasync` and
  `openAsBlob` were added; `stat()` now reports the owner set by `chown`.
- `events.listenerCount`/`getEventListeners`, `timers.active`/`enroll`/`unenroll`,
  `async_hooks.asyncWrapProviders`, `buffer.File`/`resolveObjectURL`,
  `process.getuid`/`getgroups`/`threadCpuUsage`/`finalization`/`assert` and the
  `util._errnoException` family were missing from their modules. The compatibility
  report also counts own property names on both sides now, so an existing but
  non-enumerable member (`process.pid`) is no longer scored as absent.

What the remaining behavioural boundaries actually are (export surface is 100.0% across all 55 Node modules):

| Area | Status |
|---|---|
| `path`, `url`, `querystring`, `punycode`, `os`, `tty`, `readline`, `vm`, `perf_hooks`, `string_decoder`, `timers/promises`, `stream/promises` | complete export surface, behaviour implemented |
| `events`, `stream`, `assert`, `buffer`, `module`, `worker_threads`, `net`, `fs/promises`, `child_process`, `fs`, `http`, `https` | 100% export surface; `fs` stores in virtual FS, `http`/`https` over virtual loopback, `worker_threads` runs real sibling workers with `SharedArrayBuffer` SPSC rings, and `child_process` supports both async (`spawn`/`exec`/`execFile`/`fork`) and COI sync (`spawnSync`/`execSync`/`execFileSync`) |
| `crypto` | 100% export surface: hashing, HMAC, PBKDF2, HKDF, **scrypt**, random, in-house AES (CBC/CTR/CFB/OFB/GCM), RSA PKCS#1 v1.5 + OAEP, **ECDH** on P-256/384/521, **`X509Certificate`** (PEM/DER), and **`Certificate`** (SPKAC); unimplemented algorithms (e.g. ECDSA/Ed25519/keypair generation) throw `ERR_CRYPTO_OPERATION_FAILED` rather than returning wrong bytes |
| `zlib` | 100% export surface: gzip/deflate/inflate round-trip through pako; Brotli and Zstd throw `ERR_ZLIB_UNAVAILABLE` |
| `wasi` | Preview 1 WASI host (`args`, `environ`, `clock`, `random`, virtual-FS `fd_*`/`path_*`, `poll_oneoff` clocks & fds, `runChild`, SAB-backed memories); socket syscalls return `ENOSYS` |
| `dns`, `tls`, `http2` | honest stubs with stable codes (`ENOTSUP` / DNS-over-HTTPS for `dns`); the browser cannot open raw sockets. Real networking needs the native browser-WASM profile or the host relay |
| `inspector`, `domain`, `cluster` | minimal compatibility hosts: there is no debugger agent or multi-process cluster in a worker |

Compatibility with **frameworks** is therefore bounded by three things, in order
of impact: native addons (SWC/lightningcss/oxide, Turbopack), raw sockets, and
real threads. Everything else — module resolution, ESM/CJS interop, bundler
transforms, HTTP servers on loopback — is implemented.

## HTTP over the virtual loopback

`http.request` is a real `ClientRequest`, not a `fetch` wrapper. Requests to
`localhost`/`127.0.0.1` are delivered straight to the `http.createServer` handler
in the same worker, so a proxy inside the runtime can talk to a dev server inside
the runtime without touching the network:

```js
const req = http.request({ port: 4000, path: '/api/items?limit=2', headers: { accept: 'application/json' } });
req.setTimeout(5000, () => req.destroy(Object.assign(new Error('socket hang up'), { code: 'ETIMEDOUT' })));
stream.pipe(req);            // body streaming, exactly as http-proxy-middleware does it
req.on('response', res => res.pipe(process.stdout));
```

Node semantics covered by `test/http-loopback.test.mjs` (15 cases): header
get/set/remove helpers, `auth` → Basic, `path`/`pathname`/`search` precedence,
`'finish'` before `'response'`, stream piping into the request, custom status
messages, `'timeout'` without an implicit destroy, `abort()` → `ECONNRESET`,
`ECONNREFUSED` for closed ports, `https.request` over the same virtual
transport, and `ServerResponse.assignSocket()`/`detachSocket()`. When the target port belongs to **another** virtual process (the
usual case for `npm run dev`, where Vite runs in a child worker), the request is
relayed through the kernel instead of failing, so a proxy in one process reaches
a server in another. Non-loopback `https` still uses the browser stack, and the module now
exports `STATUS_CODES` (all 63), `METHODS`, `maxHeaderSize`,
`validateHeaderName`/`validateHeaderValue`, `Agent`, `globalAgent` and the
platform's WHATWG `WebSocket` classes when present.

installed JS/WASM twin, or fails honestly with `ENOSYS` (`test/native-fallback.test.mjs`).

Known limits, measured rather than hidden:

- **Vite support is real but bounded.** The framework matrix runs Vite 6's
  Node API (plus Vite 7.3.8 under SvelteKit) with embedded WASM Rollup/esbuild
  providers: dev HTTP, TypeScript transforms, a production fixture build, React
  integration, and virtual HMR transport/invalidation pass. `vite build` now
  runs through a tested CLI compatibility path for a TypeScript entry and emits
  a production bundle. Common options in that adapter are intentionally
  limited; arbitrary CLI options, plugins, optimizeDeps and large projects are
  not established. Unsupported options fail explicitly instead of being ignored.
  Browser DOM HMR has been verified for one fixture (Vite 6, one CSS+SVG module
  graph, loopback service-worker preview): an edit reaches `import.meta.hot` and
  updates the DOM with no reload. Plugin fast-refresh (React/Vue), multi-module
  update graphs and other frameworks' HMR clients remain unverified.
- **`http` upgrade / WebSocket handshakes work on the virtual loopback, not
  across a real socket.** An in-process duplex stands in for the TCP pair: the
  client writes an RFC 6455 handshake, the server sees `'upgrade'` with one half
  and the client reads `101` from the other. That is enough for a Vite HMR client
  (verified in-browser) and for `ws`-style servers that do not inspect the
  socket. What is missing is an OS socket: `getsockname()`/`remoteAddress` are
  synthesized, backpressure and half-close are approximated, and a library that
  needs the real descriptor will notice.
- unmapped native addons (lightningcss native binaries, Turbopack, Rolldown WASI
  thread pools) cannot run in the single-threaded worker runtime, and packages
  checking the Node version see the disclosed `v22.22.3-beownir` string.

## ES modules

`require()` of an ES module works, including ESM-only packages. The loader
tokenizes the source (strings, template literals, comments and regex literals are
handled, so `"import x"` inside a string is not touched), rewrites static
`import`/`export` into CommonJS bindings and evaluates the result in a wrapper
whose parameters cannot collide with module locals (`vite` declares its own
`__dirname`).

What the transform supports, all covered by `test/esm-loader.test.mjs`:

- default, named, aliased and namespace imports; side-effect imports;
  `export default` for values, functions and classes; `export { … }`,
  `export { … } from`, `export * from`, `export * as ns from`;
- `export const/let/var`, destructuring declarations (`export const { a, b: c,
  ...rest }`, array patterns), `export function`, `export async function`,
  `export class`, generators;
- `import.meta` (`url`, `filename`, `dirname`, `resolve`) and dynamic `import()`
  in both ESM and CommonJS files, resolved through the same virtual loader;
- `package.json` `"type": "module"`, `.mjs`/`.cjs` extensions, `"exports"` maps
  with conditions and `*` patterns (so `svelte/compiler` resolves), CommonJS ⇄
  ESM interop in both directions, and circular graphs.

Exported bindings are live through getters, so `export let counter` updates when
the module mutates it, and load-time circular graphs (`export function`
hoisting, bottom exports, `export *` re-exports) resolve once exports settle.
Two deliberate limits: top-level `await` is rejected with Node's
`ERR_REQUIRE_ASYNC_MODULE` code (there is no synchronous way to wait), and
post-evaluation `export let` reassignments in a cycle update namespace objects
but remain snapshotted for destructured named imports taken during loading.

## Offline shell

`o/site/coi-sw.js` is one service worker doing two jobs, because a scope can only
have one:

1. injects COOP/COEP/CORP so the page becomes cross-origin isolated on any static
   host (SharedArrayBuffer, JSPI, WASIX);
2. caches the single-file shell (`beownir-shell-v3`, network-first for
   navigations, stale-while-revalidate for assets) so the IDE, editor and
   terminal still open with no network.

Registry traffic and `Range` requests are never intercepted — the streaming
installer owns those. `offline status` / `offline clear` in the terminal report
and rebuild the cache, and `Beownir.status().offlineShell()` exposes it to the
page.

## Node compatibility

The worker runtime aims at "modules load and common code paths work", not
byte-for-byte Node:

- `async_hooks` (`AsyncLocalStorage` scoped to the synchronous run, because a
  worker has no async hooks to propagate through timers or awaits),
  `AsyncResource`, `util.parseArgs`,
  `util.isDeepStrictEqual`, `util.types`, `util.styleText`, `buffer.isUtf8`,
  `buffer.atob/btoa`, `module.createRequire`/`builtinModules`/`isBuiltin`,
  `url.fileURLToPath`/`pathToFileURL`, `path.posix`/`win32`, `vm.Script`,
  `perf_hooks.PerformanceObserver` are implemented;
- `child_process` runs through separate workers (8 processes), including both
  async (`spawn`, `exec`, `execFile`, `fork`) and synchronous (`spawnSync`,
  `execSync`, `execFileSync` via cross-worker `SharedArrayBuffer` +
  `Atomics.wait` under cross-origin isolation, falling back cleanly to
  `ERR_NOT_SUPPORTED` when COI is unavailable); `net` covers loopback TCP,
  `http`/`https` speak the same virtual loopback (see below);
- `crypto` includes a from-scratch AES core (CBC, ECB, CTR, CFB, OFB and GCM
  with AAD and auth-tag verification), `Hash`/`Hmac` classes with `copy()`,
  `crypto.hash`, `hkdf`, Miller-Rabin `checkPrime`/`generatePrime`, the eight
  RFC modp Diffie-Hellman groups, `KeyObject`/`createSecretKey`,
  `generateKey('aes'|'hmac')` and `getCipherInfo`, `X509Certificate` and
  `Certificate` (SPKAC), plus **RSA** implemented on
  BigInt: PEM/DER/JWK key parsing, PKCS#1 v1.5 signatures, PKCS#1 v1.5 and OAEP
  encryption, all byte-identical to OpenSSL and asserted in
  `test/crypto.test.mjs` (ciphers) and `test/crypto-asymmetric.test.mjs` (keys,
  signatures, encryption, X.509/SPKAC);
- `dns` and `dns/promises` resolve over DNS-over-HTTPS, because a browser cannot
  open a UDP socket: `resolve4/6`, `resolveMx/Txt/Caa/Srv/Soa/Tlsa/Naptr/Ns/Ptr`,
  `resolveAny`, `reverse`, `lookupService`, `lookup` and `Resolver.setServers`
  all return Node-shaped records (`test/dns.test.mjs`);
- `worker_threads` runs real sibling Web Workers orchestrated by `frame-kernel`
  (up to `16` concurrent threads under cross-origin isolation with SPSC
  `SharedArrayBuffer` ring mailboxes, `MessageChannel`/`MessagePort` transfer,
  `BroadcastChannel`, `getEnvironmentData`/`setEnvironmentData`, `SHARE_ENV`,
  and `postMessageToThread`, falling back to `postMessage` when `SharedArrayBuffer`
  is unavailable); `dgram` is a virtual UDP bus that delivers to sockets bound
  in the same runtime and answers `ENOTSUP` for anything leaving the browser;
- no native addons and no `node:test` reporter runner (the `test` module
  surface exists and `describe`/`it`/`assert` drive the shell's own test
  command).

Anything unsupported throws an explicit `Error` with a stable `code` instead of
failing silently. `crypto.scrypt`/`scryptSync` (RFC 7914 Salsa20/8 + BlockMix),
`crypto.createECDH` (P-256, P-384, P-521, with compressed/hybrid point codecs and
`ECDH.convertKey`), `crypto.X509Certificate`, and `crypto.Certificate` are
implemented in-house and compared with OpenSSL. The asymmetrical gaps that
remain are key **generation** (`generateKeyPairSync` / `generateKeyPair`),
non-RSA algorithms (ECDSA, Ed25519 signing/verification), RSA-PSS padding, and
encrypted PEM keys; Brotli and Zstd need the platform's `CompressionStream`
(browsers ship gzip/deflate only), so on a real browser they fail with the
reason instead of a wrong result.

## The release artifact

`beownir-standalone.html` is built, not hand-maintained:

```bash
node tools/build-standalone.mjs          # write the artifact
node tools/build-standalone.mjs --check  # stale/tampered/missing asset -> exit 1
node tools/standalone-smoke.mjs          # verify + boot + run commands, artifact only
```

The document carries a `<script id="beownir-build-manifest">` block listing every
embedded source and native asset with its sha256, the anchors, and the three

## Running on a browser that is not your dev machine

`test/degraded-browser.test.mjs` boots the same single file with the globals a
constrained worker does not have — no `fetch`, no `crypto`/`crypto.subtle`, no
`CompressionStream`, no `SharedArrayBuffer`, no `caches`/`localStorage`/`indexedDB`,
no `navigator` — and then writes files, runs a script through the terminal,
serves a virtual HTTP request, compresses with gzip/deflate and hashes with
SHA-256/HMAC. What cannot work there fails by name (`ENOTSUP` for a missing
CSPRNG, `ENETUNREACH` for a missing network) rather than with a `ReferenceError`
at import time.

`test/node-prefix.test.mjs` and `test/developer-apps.test.mjs` cover the other
half: `require('fs')` and `require('node:fs')` are the same object,
`module.builtinModules` matches the running Node's public list, and real programs
— a routed JSON API, a CLI that reads argv and piped stdin, a stream pipeline
into gzip, an HMAC-signed token, an ESM entry with top-level `await`, a timer
queue — are written into the virtual project and run with `node app.js`.

## Host

`node o/host/beownir-host.mjs o/site/index.html` starts three servers on
consecutive ports (IDE, runtime, preview) and:

- serves the single file with COOP/COEP, `Permissions-Policy`, ETag/304 and a
  cached gzip body;
- serves the embedded runtime assets with integrity-checked ETags;
- relays registry-only TCP/WebSocket traffic and DNS-over-HTTP for the runtime,
  pinned to `registry.npmjs.org`;
- brokers preview HTTP/WebSocket traffic to the browser kernel through a
  capability-token session;
- exposes `/healthz` on each origin, shuts down cleanly on `SIGTERM`/`SIGINT`
  and refuses to start on a bad `PORT` or a missing HTML file.

Environment: `PORT` (base port), `BEOWNIR_BIND` (`127.0.0.1` by default; set `0.0.0.0` only to opt into network exposure), `BEOWNIR_IDE_ORIGIN`, `BEOWNIR_RUNTIME_ORIGIN`,
`BEOWNIR_PREVIEW_ORIGIN`, `BEOWNIR_HTML`, `BEOWNIR_LOG=1` for request errors.

## Deployment

### Netlify (single file, no build step)

Connect the repository and deploy. There is nothing else to configure: the
repository-root `netlify.toml` publishes `o/site` and sends the headers the
runtime needs.

`o/site` also carries `coi-sw.js`, the preview service worker. It is fetched
same-origin and must be served as JavaScript from the site root (the deploy
step writes the file; do not bundle or rename it). On a deployed host the worker
registers but the loopback gate keeps the same-origin preview off, so the page
behaves exactly as it did before: sandboxed `srcdoc` preview through the
rewriting loader. If the file is missing, the IDE does not attempt the worker
path at all.

```toml
[build]
  publish = "o/site"
```

Two details make or break this, and both are tested:

- **The config must be at the repository root.** Netlify only reads
  `netlify.toml` from the repository root unless the site's base directory is
  changed. `o/netlify.toml` exists for deployments that set `base = "o"`; the two
  files carry identical isolation headers and `test/deployment.test.mjs` fails if
  they drift.
- **COOP/COEP must arrive as headers.** `Cross-Origin-Opener-Policy:
  same-origin` plus `Cross-Origin-Embedder-Policy: require-corp` is what makes
  the page `crossOriginIsolated`, which is what gives the runtime
  `SharedArrayBuffer`, JSPI and the WASIX profile. A static host that cannot set
  headers still works: the page registers `coi-sw.js`, which re-serves every
  response with the same isolation headers. Without either, the IDE boots in the
  limited single-threaded profile.

`/` and `/index.html` are sent with `Cache-Control: max-age=0, must-revalidate`,
so a deploy is visible on the next visit instead of sitting behind a CDN copy.

### Opening the file directly

`o/site/index.html` is a real single file: you can download it and open it from
disk. A `file://` page has an opaque origin, though, so service workers are
unavailable (no isolation headers) and some browsers refuse to start a worker
from a `blob:` URL — which is where the runtime runs. The IDE still boots and
reports the missing capability instead of hanging, but the full profile needs a
static host or `npm run serve:static`.

### Verifying a deploy

```bash
node o/deploy/check.mjs --ide https://your-site.netlify.app/
```

It checks the status, the isolation headers, that the deployed title matches the
version in this checkout, that the page is the real 8.5 MiB artifact rather than
a placeholder, that nothing is loaded from another origin, that single-file mode
has no extra origins configured, and that `coi-sw.js` is served with the right
scope. It exits non-zero and names the first failure.

The same check runs in CI against `npm run serve:static`, which serves `o/site`
with exactly the headers from `netlify.toml` — the closest thing to the Netlify
CDN you can run locally:

```bash
npm run serve:static        # http://localhost:8080
```

### Three origins (the Node host)

The `o/host` server additionally isolates the runtime on its own origin and
brokers preview traffic. That deployment needs three hostnames:

```bash
node o/deploy/configure.mjs --runtime https://runtime.example --preview https://preview.example
node o/deploy/check.mjs --ide https://ide.example \
                        --runtime https://runtime.example --preview https://preview.example
```

## Limits

- install budgets: 64 MiB compressed / 256 MiB unpacked per package, 512 MiB and
  2,048 packages per graph, 64 MiB per file;
- dependency checkpoints: 128 MiB compressed per project;
- source workspace: half of the origin quota, floored at 64 MiB and capped at
  20 GiB, with a quarter of that per file (16 MiB floor, 256 MiB ceiling) and
  20,000 entries;
- preview request bodies: 1 MiB, preview pages: 16 MiB;
- three resident process groups; extra groups wait.

The source workspace is measured, not guessed: the editor, the ZIP importer,
`df`/`statfs`, the runtime filesystem and the browser kernel all read one rule
(`npm test` compares the two copies of it). Each file also has to become one
IndexedDB value, so the per-file ceiling stops at 256 MiB, well below V8's
~512 MiB string limit. Autosave stores one record per distinct file content,
keyed by SHA-256, plus a small manifest — a 20 GiB workspace no longer has to
fit in a single value, and a debounced save only rewrites what changed. When a
browser reports no quota (some private modes, older Safari) the budget stays at
the historical 64 MiB, so nothing regresses.

The rest are deliberate: they turn an out-of-memory crash into a clear message.
